# AGENTS.md

## Repository Purpose

This repository contains CUDA microbenchmarks for probing the numerical behavior
of NVIDIA tensor cores. It accompanies the paper:

Massimiliano Fasi, Nicholas J. Higham, Mantas Mikaitis, and Srikara Pranesh,
"Numerical Behavior of the NVIDIA Tensor Cores", PeerJ Computer Science 7:e330,
2021. DOI: 10.7717/peerj-cs.330.

The tests investigate tensor-core support for subnormal values, product and
accumulation precision, rounding behavior, accumulator normalization, carry-out
digits, and monotonicity across Volta, Turing, Ampere, Hopper, Ada, and
Blackwell-oriented build targets currently represented in the Makefile and
archived results.

## Working Boundaries

- Keep all edits inside this repository.
- Treat the result directories `3080/`, `4090/`, `5090/`, and `A10/` as archived
  experimental data. Do not rewrite, remove, or regenerate them unless the task
  explicitly asks for result updates.
- Root-level `result-*.txt` files are generated by `run_tests.py` and are not
  intended to be committed unless a task explicitly asks for new baseline data.
- Root-level `test-*` files are Makefile build products and should remain
  untracked.
- Preserve the GPL-2.0 license headers in CUDA source files.

## Build And Run

- Use `make all` to build every configured target.
- Use a narrower target when possible:
  - `make test-V100` for `sm_70`
  - `make test-T4` for `sm_75`
  - `make test-A100` for `sm_80`
  - `make test-4090` for `sm_89`
  - `make test-H100` for `sm_90`
  - `make test-5090` for `sm_120`
- Use `python3 run_tests.py` only after building the desired executables. It
  runs every root-level executable named `test-*` and writes root-level
  `result-*.txt` files.
- Use `make clean` to remove root-level executables and generated root-level
  result files.

## Development Notes

- The benchmark kernels use CUDA WMMA APIs from `<mma.h>` and precision-specific
  CUDA types such as `half` and `nv_bfloat16`.
- Prefer small, precision-specific changes over broad rewrites. Many files are
  intentionally similar so that output differences map clearly to a GPU
  architecture or numeric mode.
- When adding a GPU architecture, add explicit Makefile targets, keep executable
  names in the `test-<gpu>-<mode>` shape, and document the required compute
  capability.
- When changing numerical predicates, compare against the paper's experiment
  intent and existing archived outputs before deciding that a change is correct.
- If a local GPU does not match a Makefile target, compile-only checks may still
  be useful, but do not present generated runtime output as a result for another
  architecture.

## Verification Expectations

- For documentation or ignore-only changes, run `git status --short` and inspect
  the diff.
- For source or Makefile changes, run the narrowest relevant `make` target.
- For result changes, record the GPU model, compute capability, CUDA version,
  command used, and output file path in the final report.
